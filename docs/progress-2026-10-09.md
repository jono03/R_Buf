## 6. 아직 확인 안 된 것

- **쓰기 폭주 중 동작**: 이번 시험은 쓰기 1GB와 읽기뿐. 16GB 폭주(GC, 큐 포화)에서 기록 코드가 안정적인지는 첫 본 회차에서 처음 확인.
- **fio 로그와 짝짓기**(`--fio-log`)와 fetch-before: 본 회차 데이터로 처음 검증.
- **로그 용량**: M1 약 27만, M2 약 16만(`ROT=10`)은 계산값. 실제 건수는 본 회차에서 확인.
- **덤프 시간**: 이번 2.7MB 덤프에 걸린 시간을 재지 못함. 본 회차(M1 약 17MB)에서 측정.
- **S-Buf 빌드(`RBUF_ENABLE=0`)**: 아직 빌드·부팅하지 않음. 배너 `RBUF=0`, R-Buf 엔트리 플래그 0% 확인 필요.
- **부팅 로그의 Erase FAIL / bad block 출력**: 모든 채널에서 같은 블록 번호가 불량으로 잡히고 `bad block table ... does not exist`가 출력됨. 예전 부팅 로그에도 같았는지 **확인 필요** (제 코드 변경과 무관한 보드 쪽 출력으로 보임).
- **`dmesg` timeout/abort/reset**: 시험 후 결과 미확인.

## 7. 환경 메모

- 부팅 후 **호스트 PC는 `Turn on the host PC` 메시지가 나온 뒤에** 켠다.
- `~/m12`는 이 호스트 PC에 없었음 → `mkdir -p ~/m12`로 새로 만듦. `rbuf_check.fio`는 아직 없음(계획서 2절 내용으로 생성 필요).
- JTAG 덤프는 Windows(SDK) PC의 XSCT에서 수행. 해석은 같은 PC에서 python 3.12.10으로 수행(`C:\Users\User`에 `trace_parse.py`, `test_trace.bin`).
- XSCT는 Tcl 창이라 python 명령을 입력하면 안 되고, 일반 명령 프롬프트에서 실행.
- 파일 위치: `C:\Users\User\Desktop\3조\10-09\trace-final-2026-10-09\` (zip과 푼 폴더).
- SDK 프로젝트: `run-rbuf09` (복사본). 원본 `run-rbuf`, `run-rbufsuccess`는 건드리지 않음. Run 설정에서 ELF를 `run-rbuf09.elf`로 골라야 함(목록에 `run-gftl3.elf`가 먼저 선택돼 있었음).
- ELF는 빌드할 때마다 같은 경로에 덮어써지므로 **빌드 직후 `rbuf-trace.elf` / `sbuf-trace.elf`로 복사해 둘 것**.

## 8. 다음 순서

1. 현재 R-Buf ELF를 `rbuf-trace.elf`로 복사.
2. `RBUF_ENABLE=0`으로 Clean → Build, `sbuf-trace.elf`로 복사.
3. 호스트에 `rbuf_check.fio` 생성(계획서 2절).
4. **S1** (S-Buf, M1, `TAG=sbuf_m1_r1`, `RQD=1 ROT=60`) 시작. 이 회차는 시험 회차 겸용: 덤프 시간 측정, fio 짝짓기 확인.
5. 이후 순서: R1 → S2 → R2 → M2 S → M2 R → 점심(해석) → S3 → R3.
