# 2026-10-09 하루 정리 (본 실험 8회 완료)

이 문서는 10/9에 한 일 전체를 한 곳에 정리한 것이다. 숫자는 모두 이 날 사용자가 보낸 실제 출력(`mrd` 헤더, `trace_parse.py`, `awk`, `fio` 요약, `dmesg`)에서 가져왔고, 계산한 값은 계산했다고 표시했다.
이전에 따로 만든 문서(`progress-2026-10-09.md`, `results-2026-10-09.md`, `session-summary-2026-10-09.md`, `work-split-2026-10-09.md`)는 중간 시점의 기록이며, 이 문서가 최종 정리이다.
팀 문서(README, firmware-spec, 절차 v8.2)는 저장소에 없어 확인하지 못했다. 다르면 팀 문서가 우선한다.

## 1. 한 줄 요약

- 계측 빌드(커밋 `2340e73`)를 보드에서 처음 돌려 **본 실험 8회**(M1 S/R 각 3회, M2 S/R 각 1회)를 모두 측정했다. 각 회차의 펌웨어 기록과 호스트 로그가 Drive에 있다.
- **펌웨어 서비스 구간 안**: R-Buf는 읽기의 버퍼 대기를 없앴고(`bufReadEvictCnt` 0), 남는 대기는 die 큐다. 펌웨어 내부 최대 지연은 R-Buf 약 10 ms, S-Buf 21~29 ms. **펌웨어 안에서는 1초 이상 정지가 한 번도 없었다.**
- 호스트(fio)는 QD1 읽기에서 1~24초 정지를 봤다. 이 정지는 펌웨어 서비스 구간 밖에 있다. 논문 스코프는 펌웨어 안쪽으로 정했으므로 이 부분은 한계로 적는다.
- 아직 안 한 분석: 폭주 구간만의 꼬리 비교(`trace_phases.py`), die 대기 대 메인 루프(`trace_loopdie.py`). 도구는 만들었고 실제 데이터로는 아직 안 돌렸다. (정지 위치는 이 문서 작성 뒤의 추가 실험으로 정리됨: 15절)

## 2. 스코프 (정리)

- 논문 질문: R-Buf 이후에도 남는 읽기 대기가 **펌웨어 안 어디서** 생기는가. 구간은 버퍼 / die 큐 / 메인 루프 / 읽기 전송 대기 / NAND+DMA.
- 처음에 호스트 정지와 인터럽트 쪽으로 분석을 넓힌 것은 스코프를 벗어난 일이었다. 지금은 "펌웨어 안쪽만 본다"로 둔다. 호스트 정지와 인터럽트 이상은 관찰 사실로만 기록하고 논문에는 한계 한두 문장으로 쓴다.
- 이 스코프에서 이미 나온 결과: 펌웨어 안에서는 초 단위 정지가 없다. 팀 문서의 주장("R-Buf 이후에도 초 단위 정지가 남는다")과 어떻게 맞출지는 팀 확인이 필요하다.

## 4. 환경과 절차

**장비 구성**
- 호스트(리눅스): fio, `~/m12`. 보드를 NVMe 디스크로만 본다.
- Windows PC: SDK, JTAG(덤프), SDK Terminal(UART, COM3 115200), python.
- 덤프는 JTAG이 연결된 Windows PC의 XSCT에서만 가능하다. 보드 DRAM의 기록은 재부팅하면 사라지므로 덤프를 마치기 전에 보드를 끄지 않는다.

**한 회차 절차**
1. Windows: SDK Terminal 비우기, `ftl_config.h`의 `RBUF_ENABLE` 0/1 설정, Clean → Build, ELF를 `elf_backup\`에 백업.
2. 호스트 끄기 → FPGA 프로그램 → `run-rbuf09.elf` 실행 → 배너 확인 → `Turn on the host PC` 후 호스트 켜기.
3. 호스트: `~/m12/run_one.sh <TAG> <RQD> <ROT>`(DEV 확인, 중복 방지, 인터럽트 전후, fio, `dmesg` 전체, 묶기).
4. 덤프: `mrd 0x00300000 8`로 recCount N 확인 → `mrd -bin -file <TAG>_trace.bin 0x00300000 <1024 + N×16>` → 크기 `4096 + N×64` 확인.
5. Drive `3조/10-09/data/<TAG>/`에 `host.tgz`(호스트), `trace.bin`, `boot_<TAG>.txt`(Windows) 업로드, `runlog.md` 한 줄.

**fio 구성(`rbuf_check.fio`)**: prefill 8GiB 쓰기 → `ro`(읽기만 ROT초) → reader(4KB 랜덤 읽기, QD=RQD) + writer(16KB 랜덤 쓰기 QD32 16GiB). 읽기 영역 0~8GB, 쓰기 영역 8~24GB. M1은 `RQD=1 ROT=60`, M2는 `RQD=8 ROT=10`.

**기록 형식**: version 3, 64바이트 레코드, DRAM `0x00300000`, 타이머 500 MHz(시간 단위 0.128 µs), 최대 50만 건.

### 6-4. QD8 처리량 비교 (M2, 각 1회, fio 요약)

### 7-3. 호스트 `dmesg`와 인터럽트

| 회차 | `Disabling IRQ #150` | `I/O ... timeout, completion polled` |
|---|---|---|
| S1 | 확인 불가(그때는 `timeout\|abort\|reset`만 저장) | 없음 |
| R1 | 167.5 s | 300.7 s |
| S2 | 181.1 s | 313.8 s |
| R2 | 134.97 s | 없음 |
| M2 S | 90.3 s | 없음 |
| M2 R | 92.4 s | 없음 |
| S3 | 104.0 s | 233.9 s |
| R3 | 118.5 s | 없음 |

- IRQ 150은 관리 큐(`nvme0q0`)다. R1의 `/proc/interrupts`에서 이 큐에 **199,893**번의 정체 불명 인터럽트가 들어와 커널이 비활성화했다. I/O 큐(`q1~q7`) 인터럽트 합(1,383,365)은 완료 수(1,383,606)와 거의 같았다.
- `Disabling IRQ #150`은 S1을 제외한 7회 모두에서 나왔고 I/O timeout은 3회(S2, S3, R1)에서만 나왔다. IRQ 150 비활성화만으로 I/O timeout이 생기지는 않는다. 10/7 기록에도 `Disabling IRQ #150`이 한 번 있었다.
- 이 절의 초안은 "원인은 모른다"였다. 이후 폴링 대조 실험(15-2절)으로 호스트 정지가 완료를 인터럽트로 받을 때만 생기는 것이 확인되었다. 인터럽트가 **왜** 빠지는지(보드 MSI-X 쪽인지 호스트 쪽인지)는 확인하지 않았다.

`trace_loopdie.py`의 원리: `SchedulingNandReq()` 한 번 호출은 모든 채널을 한 바퀴 도는 것이다(코드 확인). 큐 삽입(`dEnqueue`)에서 트리거 발행(`dIssue`)까지의 창 W와 호출 수(`schedDieQ`)로 평균 폴링 간격 = W ÷ (호출 수 + 1)을 구하고, 루프가 만든 지연을 최대 (앞선 요청 수 + 1) × 간격으로 추정한다. 나머지는 die·채널이 실제로 바빴던 시간이다. 평균 기반 추정이라 한 번의 긴 공백은 안 보인다.

## 13. 논문에 쓸 수 있는 것 / 쓰면 안 되는 것

**쓸 수 있는 것(근거 있음)**
- R-Buf는 읽기가 쓰기 내려쓰기를 기다리는 대기를 없앴다(`bufReadEvictCnt` R-Buf 4회 0, 꼬리 읽기 버퍼 대기 54% → 0%).
- R-Buf 이후 펌웨어 내부에 남는 대기는 die 큐(꼬리 읽기의 약 95%).
- 펌웨어 내부 읽기 최대 지연은 R-Buf에서 약 10 ms(세 회차 일관), S-Buf에서 21~29 ms. 펌웨어 안에서 1초 이상 정지는 없었다.
- QD8에서 R-Buf는 폭주 중 읽기 처리량 +34%, 쓰기 −3.4%, 읽기만 −7.3%이고, 버퍼 대기가 다시 나타난다(원인: 15-1절의 칸 재사용 막힘, 우리 최소 재구현의 성질).
- 한계: 호스트 fio에서는 QD1 읽기가 쓰기 폭주 중 초 단위로 정지했고(S-Buf 3~4건, R-Buf 10~16건) 이 정지는 펌웨어 서비스 구간 밖에 있다. 호스트 NVMe 인터럽트 이상(IRQ 150 비활성화)이 관찰되었다.

**쓰면 안 되는 것**
- "정지는 fetch-before다", "R-Buf가 정지를 늘렸다/줄였다"(변동이 크다), "인터럽트가 빠지는 이유는 보드 MSI-X다/호스트다"(미확인). ("인터럽트 때문에 정지한다"는 폴링 대조(15-2절)로 근거가 생겨 쓸 수 있다.)
- 전체 읽기 p99로 S-Buf와 R-Buf의 크기를 말하는 것(폭주 구간 분리 전).
- `trace_phases.py`, `trace_loopdie.py`로 얻을 결론(실제 데이터로 아직 안 돌림).

### 15-1. 진단 실험 `rbuf16_m2_r1` (M2 R-Buf, 읽기 칸 16)

| 항목 | 내용 |
|---|---|
| 목적 | M2 R-Buf에서 버퍼 대기가 다시 나타난 원인 확인 |
| 변경 | `RBUF_ENTRY_COUNT`를 `(2 * USER_DIES)` = 16으로(쓰기 칸 112), 나머지는 M2 R과 같음. 1회. 실험 뒤 8칸으로 되돌려 다시 빌드 |
| 기록 | recCount 426,590, 1초 이상 정지 0건, `bufReadEvictCnt` 0, GC 0, IRQ150 비활성(301.2 s), timeout 없음. Drive `3조/10-10/data/rbuf16_m2_r1/` |

| | 칸 8 (`rbuf_m2_r1`) | 칸 16 (`rbuf16_m2_r1`) |
|---|---|---|
| p99 초과 읽기의 buffer / dieq (전체 읽기 기준 `trace_parse`) | 64.0% / 34.7% | 37.6% / 60.4% |
| 펌웨어 p99 / max | 15.6 / 38.8 ms | 10.5 / 27.8 ms |
| `check_wrap.py`: 버퍼 대기 중 "N번째 앞 읽기가 진행 중"으로 설명되는 비율 | **99.7%** | **99.2%** |
| 같은 계산을 N±1로 (대조) | 24~30% | 12~13% |
| 막힘 해제 − 앞 읽기 끝난 시각 (중앙값) | 0.006 ms | 0.006 ms |

- **코드 확인(저는 확인함):** `data_buffer.c`의 `AllocateDataBuf()`는 읽기에 대해 `rbufLruList.tailEntry`를 그대로 꺼내고 그 칸이 아직 앞선 요청에 사용 중인지(`blockingReqTail`)를 보지 않는다. 이후 `UpdateDataBufEntryInfoBlockingReq()`가 새 요청을 그 칸의 앞 요청 뒤에 매달고 `CheckBufDep()`이 `prevBlockingReq`가 있으면 막는다. 이것이 trace의 buffer 구간(`dBufAlloc` → `dEnqueue`)이다.
- 따라서 QD8에서 쓰기 프로그램 뒤에 걸린 느린 읽기 하나가 칸을 붙잡으면, 칸을 한 바퀴 돌려 그 칸을 받은 읽기가 막힌다(head-of-line). 칸을 16개로 늘리면 한 바퀴가 길어져 줄지만 사라지지 않는다. 칸 16 > 동시 읽기 8인데도 남으므로 **"칸 8 = 동시 읽기 8이라 소진된다"는 초안 가설은 틀렸다(철회).**
- M1(QD1)에서 R-Buf 버퍼 대기가 0%인 것과도 맞는다(동시에 진행 중인 다른 읽기가 없다).
- **범위:** 우리 최소 재구현의 성질이다. 원 논문 구현이 사용 중인 칸을 건너뛰는지는 확인하지 않았으니 원 논문 R-Buf의 한계로 쓰지 않는다. 처방 후보(12월): LRU 꼬리부터 사용 중이 아닌 칸을 고르기.
- 한계: `check_wrap.py`와 원자료는 제가 보지 못했다(`check_wrap.py`는 파일을 받지 못함). 칸 16은 1회 실험이다.

| 본 실험 R1~R3 | R-Buf | 기본 | 인터럽트 | 11 / 16 / 10건 | - |
| `rbuf_m1_poll1` | R-Buf | 인터럽트 4 + 폴링 4 | **폴링** | **0건** | 307,384 |
| `rbuf_m1_q4int1` (대조) | R-Buf | 인터럽트 4 + 폴링 4 | 인터럽트 | **9건** (1.1~18.6 s) | 274,557 |
| `sbuf_m1_poll1` | S-Buf | 인터럽트 4 + 폴링 4 | **폴링** | **0건** | 274,370 |
| `rbuf_m1_poll2` | R-Buf | 인터럽트 4 + 폴링 4 | **폴링** | **0건** | 306,776 |

- 네 회차 모두 GC 0, 전체 erase 부팅, 관리 큐 IRQ 비활성화(이번 부팅들은 IRQ 146), I/O timeout 없음.
- 호스트 설정: `nvme.poll_queues=4`(GRUB), 이후 원복. 폴링 fio 파일은 `ro`·`reader`에 `ioengine=io_uring`, `hipri=1`을 추가. 실행은 `run_one_poll.sh`(`run_one.sh`와 큐 구성 저장, `io_poll` 확인만 다름).
- **큐 구성 변경은 대조로 배제했다:** 폴링 큐를 만들면 Cosmos의 인터럽트 큐가 4개로 줄어든다. 같은 구성에서 폴링만 끈 회차(`q4int1`)에서 정지 9건이 나왔고 폴링 3회는 0건이므로, 정지를 없앤 것은 큐 구성이 아니라 폴링이다.
- 폴링 R-Buf 회차의 recCount가 약 3만 건 많다(정지 없이 폭주 중에도 읽기가 계속 처리됨).
- **결론(결과로 쓸 수 있음):** 호스트에서 보이던 1~24초 읽기 정지는 읽기 완료를 인터럽트로 받을 때만 생기고 폴링으로 받으면 사라진다. 이것은 제가 세웠던 "완료 알림 유실" 가설과 같은 방향의 개입(인터벤션) 증거다.
- **여전히 모르는 것:** 인터럽트가 왜 빠지는지(보드 MSI-X 쪽인지 호스트 쪽인지). 관리 큐 벡터에 정체 불명 인터럽트 약 20만 번, 대부분의 회차에서 IRQ 비활성화가 관찰된다는 사실까지만 쓴다.
- 한계: 대조 회차(`q4int1`)가 1회, 폴링 3회다. 폴링 회차의 "0건이 측정 실수가 아님"(reader 실행 시간, fio `err`, 인터럽트 증가량)은 분석 담당이 확인하기로 했다. 저는 이 4회의 원자료를 보지 못했다.
