# 초안 A 재구성 제안: "따로 노는 느낌"을 없애는 흐름과 표 — 2026-10-11

`draft-A-review-2026-10-11.md`(사실 검토)의 후속입니다. 이 문서는 읽히는 흐름과 표·그림을 다룹니다. 아래 본문 예시의 숫자는 모두 저장소 실측 기록과 소스로 확인한 값만 썼습니다.

## 1. 왜 따로 노는 느낌인가 (진단)

1. **"한 일의 목록" 순서입니다.** 배경 → 구현 → E1 비교 → 계측 → 구간 → 워크로드 → 환경 → 분석 규칙이 모두 같은 무게로 나열됩니다. 읽는 사람이 "그래서 이게 무슨 질문의 답을 위한 건데?"를 문단마다 다시 추측해야 합니다.
2. **논문이 말하려는 한 문장이 2~4절 어디에도 없습니다.** 팀 문서의 핵심은 "R-Buf를 써도 읽기가 몇 초씩 멈춘다. 그 멈춤은 펌웨어가 읽기를 처리하는 구간 밖에서 생기고, 읽기 완료를 폴링으로 받으면 사라진다"입니다. 읽는 사람이 이 문장을 모르면 배경도 방법도 목적 없이 읽힙니다.
3. **절이 서로를 부르지 않습니다.** 3.3의 E1 비교(R-Buf가 잘 동작한다)는 주장과 직접 이어지지 않고, 4.2 구간 정의와 4.5 위치 판정은 "왜 펌웨어 기록과 호스트 지연을 둘 다 재야 하는가"라는 이유를 먼저 말하지 않습니다. 구현 절의 칸 재사용 막힘도 빠져 있어 결과가 갑자기 나옵니다.
4. **표가 같은 종류의 정보(숫자 격자)라 비교가 안 됩니다.**
   - 표 1(원 논문 비교)은 4행 × 3열인데 주장과 관계가 약해서 눈에 안 들어옵니다.
   - 표 2(구간 정의)는 정의라서 그림 한 장이 더 잘 보여 줍니다.
   - 정작 읽는 사람이 보고 싶은 것은 "정지가 어디서 몇 번 생겼나"입니다. 이 표가 없습니다.

## 2. 고치는 원리: 질문 하나가 2~4절을 꿰게 한다

### 2.1 논문의 한 줄과 세 질문

- **한 줄(서론 끝에도 넣을 문장):** "지속 쓰기 폭주에서 R-Buf를 써도 읽기가 초 단위로 멈추는 일이 남는다. 요청별 펌웨어 기록으로 보면 이 멈춤은 펌웨어가 읽기를 처리하는 구간 밖에서 생기며, 읽기 완료를 폴링으로 받으면 사라진다."
- 이 한 줄을 세 질문으로 풀어 쓰면 방법과 결과의 뼈대가 됩니다.

| 질문 | 필요한 도구(방법 절) | 결과 절의 답 |
|---|---|---|
| Q1. R-Buf가 읽기의 버퍼 대기를 없앴나? | 구현(읽기·쓰기 영역 분리), 내려쓰기 카운터 | 읽기가 일으킨 내려쓰기 0회, QD1 버퍼 대기 0.0~0.1% |
| Q2. 펌웨어 안에 남는 꼬리는 어느 구간인가? | 구간 분해(요청별 기록) | R-Buf QD1 꼬리의 94.6~96.2%가 die 큐 |
| Q3. 호스트가 보는 초 단위 정지는 펌웨어 안인가? | 두 시계(펌웨어 기록 + 호스트 fio), 완료 방식 대조 | 펌웨어 시간은 0.35~1.24 ms(R1 5건), 폴링 0건 / 인터럽트 9건 |

### 2.2 절마다 "이 절이 무슨 질문의 도구인가"로 시작

- 2절(배경·구현): "무엇을 비교하나(S-Buf vs R-Buf)"와 "읽기 한 건이 장치 안에서 어떤 길을 가나" → 그림 1.
- 3절(측정 방법): "그 길의 어디서 시간이 쓰이는지, 호스트가 본 시간과 어떻게 이어 보는가" → 그림 1 위에 구간을 겹침.
- 4절(결과): Q3(주 결과) → Q2 → Q1 → QD8 보조. (v23: 호스트 정지가 주 결과.)

### 2.3 E1(원 논문 방식 비교)은 짧게

- 주장의 일부가 아니라 "구현이 원 논문과 같은 방향으로 동작한다"는 확인입니다. 구현 절에서 한두 문장 + 결과 절 끝에 한 줄, 표 1은 3행만 남기거나 본문 문장으로 줄이세요. (`draft-A-review` 3.6, 5절)

### 2. 배경과 구현

**2.1 read stall과 R-Buf.** 버퍼가 가득 찬 상태에서 읽기 미스가 나면 교체 대상(victim)을 골라야 하는데, victim이 dirty이면 먼저 NAND에 내려써야 하므로 읽기 응답이 늦어진다. 이를 read stall이라 한다[1]. 읽기와 쓰기가 한 버퍼를 함께 쓰는 구조(S-Buf)에서 흔한 문제이고, R-Buf[1]는 버퍼를 읽기 영역과 쓰기 영역으로 나눠 쓰기가 읽기에 미치는 간섭을 없앤다. 원 논문에서 읽기만 할 때 대비 쓰기와 섞을 때의 평균 읽기 지연은 S-Buf에서 8.8배, R-Buf에서 1.1배였다[1]. 본 논문이 묻는 것은 그다음이다. **버퍼 대기가 사라지면 쓰기가 계속 몰리는 상황에서도 읽기는 더 이상 멈추지 않는가?**

**2.2 읽기 한 건의 경로.** 실험 대상은 Cosmos+ OpenSSD[2]의 GreedyFTL 기반 펌웨어이다. 호스트 읽기는 slice 단위로 쪼개져 버퍼 할당, NAND 읽기, 호스트 DMA 순으로 처리된다(그림 1). 버퍼 hit이면 NAND를 건너뛴다. NAND 읽기는 해당 die 큐에서 앞선 쓰기·erase가 끝나기를 기다린 뒤 트리거와 전송 두 단계로 수행되며, 채널 스케줄러는 읽기 트리거, erase, 쓰기, 읽기 전송 순으로 내보내 읽기 전송의 우선순위가 가장 낮다. 이 모든 처리는 단일 메인 루프가 폴링으로 수행한다. 처리를 마친 읽기는 완료 큐에 기록되고 인터럽트로 호스트에 알린다[3]. 호스트는 인터럽트 대신 폴링 큐로 완료를 직접 확인할 수도 있다[4].

**2.3 최소 R-Buf 구현.** 공개 펌웨어는 NVMe 레지스터 구성이 달라 우리 보드에 쓸 수 없어, 원 논문의 R-Buf를 필요한 부분만 다시 구현했다. 128엔트리(16 KB, 총 2 MB)의 버퍼를 읽기 8엔트리와 쓰기 120엔트리로 나누어(원 논문의 2 MB : 30 MB와 같은 1:15) 각각 독립된 LRU 리스트로 관리한다. 쓰기가 읽기 칸의 주소에 닿으면 그 읽기 칸을 폐기해 읽기 영역에는 clean 엔트리만 남긴다. 읽기 미스는 읽기 리스트의 LRU 꼬리 칸을, 그 칸이 아직 사용 중인지 확인하지 않고 받는다(최소 구현의 성질). `RBUF_ENABLE` 스위치로 S-Buf와 R-Buf를 같은 소스에서 빌드한다. 정합성은 16 MB 영역 16 KB 랜덤 읽기·쓰기 50:50(QD32, 256 MB)의 CRC32C 검증에서 오류가 없었고, 버퍼 로직을 호스트에서 20만 회 무작위로 돌린 테스트도 통과했다. 원 논문 방식의 비교(E1)에서도 R-Buf는 읽기 지연 배수와 읽기 IOPS가 같은 방향으로 개선되었다(4.4).

### 3. 측정 방법

**3.1 두 시계로 같은 읽기를 본다.** 호스트 지연만 보면 읽기가 멈춘 위치를 알 수 없다. 그래서 펌웨어가 읽기마다 처리 단계별 시각을 DRAM 예약 영역에 기록하고(해상도 0.128 µs), 측정 후 꺼내 분석한다. 기록하는 시각은 펌웨어가 읽기 처리를 시작한 시각, 버퍼 칸 할당, NAND 요청 큐 진입, 같은 die의 직전 요청 완료, 읽기 트리거·전송 발행·완료, DMA 시작·끝이다. 호스트에서는 fio가 읽기마다 지연을 재고, 두 기록을 요청 순서와 LBA로 짝지었다(모든 회차에서 전부 짝지어짐 [분석 담당 확인]). 두 시계는 서로 맞춰져 있지 않으므로 시각이 아니라 구간 길이만 쓴다. **호스트 지연에서 펌웨어 내부 지연을 뺀 나머지를 펌웨어 밖 시간이라 한다**(그림 1).

**3.2 구간.** 펌웨어 내부 지연을 다섯 구간으로 나눈다: 버퍼 대기, die 큐 대기, 루프 지연(메인 루프가 늦게 알아챈 시간), 읽기 전송 대기, NAND·DMA. 완료는 메인 루프의 폴링으로만 확인되므로 NAND·DMA와 die 큐 대기에는 루프 지연이 일부 섞일 수 있다. 계측 빌드의 읽기만 구간 처리량은 계측 없는 빌드(4,364 IOPS)보다 약 1% 낮았다(0.9~1.4%) [fio 출력으로 재계산].

**3.3 워크로드와 실험.** 쓰기가 NAND 처리 속도(실측 약 200~230 MiB/s)보다 계속 빠르게 도착하면 버퍼는 내려쓰기를 기다리는 데이터로 가득 찬다. 이를 **지속 쓰기 폭주**라 하고 이 상태의 읽기를 잰다. 매 회차 보드를 새로 부팅해 사용자 영역을 지우고 읽기 영역 8 GiB를 채운 뒤, 읽기만 구간(60초)과 폭주 구간(16 KB 랜덤 쓰기 QD32 16 GiB, 2초 뒤 같은 읽기 시작)을 차례로 실행한다. 쓰기 총량이 장치 여유 공간(약 64 GiB)보다 작아 GC는 모든 회차에서 0회였다. 실험은 표 1과 같이 총 14회이다. 완료 방식 대조는 커널 인자 `nvme.poll_queues=4`로 인터럽트 큐 4개와 폴링 큐 4개를 두고, 읽기만 폴링(io_uring + hipri)이나 인터럽트(libaio 또는 io_uring, hipri 없음)로 바꾼 것이다. 쓰기는 모든 회차에서 libaio(인터럽트)이다.

**3.4 분석 규칙.** 백분위는 폭주 구간의 읽기만으로 계산한다(읽기만 구간과 섞으면 회차마다 두 구간의 읽기 수 비율이 달라 비교가 깨진다). 구간은 펌웨어 기록의 처리 시작 시각으로 나눈다. 호스트 지연 1초 이상을 정지라 하고, 실행 종료 시점의 마지막 1건은 따로 표시한다. M1은 앞 읽기의 완료를 받아야 다음 읽기를 보내므로, 정지한 읽기의 앞 간격(앞 읽기 완료 → 정지한 읽기 수신)과 뒤 간격(정지한 읽기 완료 → 다음 읽기 수신)을 보드 타이머로 비교한다. 뒤 간격이 길면 정지는 펌웨어가 읽기를 끝낸 뒤에 생긴 것이다. 정지 사건의 구간 위치(1층)를 주 결과로, p99 이상 읽기에서 한 구간이 50%를 넘고 3회 모두 1위이면 그 구간을 지배 원인으로 보는 규칙(2층)을 부 결과로 보고한다(실험 전에 고정한 규칙).

**환경.** Cosmos+ OpenSSD 4채널 × 2 way(die 8개), die당 2,048블록, 노출 용량 61.8 GB, SLC 모드, 펌웨어는 SDK Debug 빌드(-O0). 호스트는 [Ubuntu 22.04, Linux 6.8.0, fio 3.28(libaio, O_DIRECT)], NVMe I/O timeout 30초 [host_info 확인].
