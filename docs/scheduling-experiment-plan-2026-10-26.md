# die queue 읽기 우선 스케줄링 — 구현·실험 계획 (보수적) — 2026-10-26

목표: R-Buf 위에서 **die queue 안의 읽기 요청을 대기 중인 쓰기 요청보다 앞에 두어** 읽기 지연시간(특히 `W_die`와 p99)을 줄이는지 측정한다.
성격: 시간·회차 수는 **추정**이다(근거는 아래에 적음). 실제 구현은 아직 하지 않았다. 코드는 `lab-rbuf`를 읽기만 했다.

## 1. 설계 요약 (코드 근거)

- 현재: 요청은 die 큐 끝에 붙고(`PutToNandReqQ`, `request_allocation.c`), 헤드가 실행 중인 요청이며 완료 시 헤드만 제거된다(`GetFromNandReqQ`). 읽기 우선은 각 die의 헤드끼리만 비교한다(`request_schedule.c`).
- 끼워 넣을 자리: `SchedulingNandReqPerCh`에서 die가 쉬게 된 뒤 새 헤드를 우선순위 표에 올리는 두 곳(약 165행, 198행), `PutToNandWayPriorityTable` 직전. 여기서 `ReorderNandReqQ(ch, way)`를 호출해 대기 중인 읽기 하나를 헤드로 옮긴다.
- 큐는 `prevReq`/`nextReq` 이중 연결 리스트라 중간 요청을 빼서 헤드에 넣는 것은 포인터 조작이다.
- **재정렬 조건:** 헤드가 처음 시작하는 요청일 때만(`READ_TRANSFER`가 아니고 재시도 중이 아님). 읽기는 트리거가 끝나면 같은 요청이 `READ_TRANSFER`로 바뀌어 헤드에 남고, 실패 시 재시도도 헤드가 유지되며 `retryLimit`가 die별 상태이기 때문이다(`ExecuteNandReq`).
- **의존성 장벽:** 앞선 쓰기·지우기와 같은 물리 블록이면 앞지르지 않는다. 기존 코드에는 row-address 의존성 처리(`blockedByRowAddrDepReqQ`, `permittedProgPage`)가 있어 읽기가 큐에 들어올 때 일부 의존성은 이미 걸러진다. 재정렬 규칙이 이것과 어떻게 겹치는지는 코드를 더 읽어 확인해야 한다.
- 쓰기 기아 방지 C: die별 카운터. QD1에서는 읽기가 하나뿐이라 작동하지 않는다. 첫 구현에서는 제외한다.
- 규칙: 실행 중인 요청은 건드리지 않음(비선점), 읽기끼리와 쓰기·지우기끼리의 순서 유지, 첫 대기 읽기가 안전하지 않으면 이후 읽기도 앞당기지 않음(보고서 설계와 같음).

## 2. 앞 실험과 맞추기 (sync)

**고정할 것**
- 빌드: 계측 빌드(커밋 `2340e73`)에 스케줄링만 추가. 컴파일 플래그(예: `DIEQ_READ_PRIORITY`)로 켜고 끄며, 끄면 앞 빌드와 같은 동작. 레코드 형식(64B, v3)과 계측 지점은 변경하지 않는다.
- 부하: `rbuf_check.fio` 그대로(prefill 0~8GB 128KB, 읽기 4KB, 쓰기 16KB QD32 8~24GB, reader 2초 뒤, `exitall`). QD1 `ROT=60`, QD8 `ROT=10`.
- 부팅 조건: 전체 erase(테이블 없음)로 통일(앞 회차는 부팅 조건이 섞였음).
- 호스트: 같은 PC, 커널 6.8.0, fio 3.28, **폴링 설정 없는 기본 상태**를 `/proc/cmdline`로 확인(앞 폴링·uring 대조의 `nvme.poll_queues=4`가 남아 있으면 안 됨).
- 분석: `core_analysis.py`, `flood_tail`을 같은 규칙으로(쓰기 구간은 fio 로그 건수로 분리, p99 초과 집합은 분석 전 고정). `trace_phases`, `trace_loopdie`는 사용하지 않는다.
- 반복과 순서: 구성당 3회, 대조와 제안을 번갈아 실행. 마지막 읽기 한 건의 30초 timeout 처리 규칙도 앞과 같다.
- 같은 프레임 수끼리 비교(8은 8끼리, 16은 16끼리).

**관문 (통과해야 새 결과를 믿을 수 있음)**
플래그를 끈 빌드로 QD1을 3회 먼저 돌려 앞 R-Buf 결과와 대조한다.

| 항목 | 앞 R-Buf QD1 값 |
|---|---|
| p50 / p99 / max | 0.66 / 9.06~9.16 / 10.0~10.2ms |
| T_die | 0.58ms |
| recCount | 약 27만(269,130~273,971) |
| 선행 요청 최대 | 15 |
| W_etc | 0.01ms 미만 |
| GC | 0회 |

벗어나면 스케줄링 코드를 의심하기 전에 환경과 빌드 차이를 먼저 찾는다.

**제안 회차에 추가로 기록할 것:** 앞지른 읽기 횟수, 장벽 때문에 못 앞지른 횟수(핵심 안전장치). 식 (4) 모형 `(k−½)T`는 제안에서 성립하지 않으므로 이 카운터로 보완한다. 레코드에 넣을 여유 필드가 있는지는 코드를 봐야 알고, 없으면 UART 카운터와 요약 파일로 대신한다.

## 3. 회차 수와 시간 (과거 실험 기반 계산)

- 한 회차: 계획 값 15~20분(부팅 약 5분 + 호스트 확인 약 2분 + fio 약 3분 + dmesg·덤프 약 3분 + 점검 약 1분). 실제 소요는 기록이 없다(덤프 시간 미측정).
- 쓰기 비용(IOPS)은 같은 회차의 `write_iops_log`(1초 평균)에서 나오므로 따로 돌릴 회차는 없다.

| 구성 | 새 회차 | 시간(15~20분/회) | 여유 25% 포함 |
|---|---|---|---|
| **최소 A (QD1만)** | 제안 QD1 3 (+ 대조 1) | 3~4회 | 약 1~1.5시간 |
| **최소 B (QD1+QD8)** | A + 제안 QD8 3 + R-Buf FIFO QD8 보충 2 | 8회 | 약 2.5~3.5시간 |
| **보고서 계획 필수** | 기준 보충 6 + 제안(프레임 8·16 × QD1·QD8 × 3) 12 + 16프레임 FIFO QD1 3 + 한도 없음 3 + C 4값 9 | 33회 | 약 10~14시간 |
| 유입률 조건 포함 | + 12(가정: 수준 2개) | 45회 | 약 14~19시간 |

- 최소 A만으로도 "R-Buf 대비 `W_die`와 p99가 줄었는가"는 확인할 수 있다. 효과가 보이면 B로 간다.
- 1회만 도는 것은 동작 확인용으로만 쓴다(앞 QD1 R-Buf는 회차 간 변동이 작았지만 제안은 모른다).
- **기록 용량 주의(추론):** 최대 50만 건인데 QD8 R-Buf 16프레임이 이미 42.7만 건이라, 읽기가 빨라지면 QD8에서 넘칠 수 있다. 첫 QD8 회차에서 확인하고 ROT나 쓰기 구간을 조정한다.
- C(1, 2, 4, 8) 비교는 QD8 이상에서만 의미가 있다. QD8에서도 읽기가 8개 die에 흩어지면 한 die에 읽기가 연속으로 쌓이는 경우가 드물어 차이가 안 날 수 있다(추론). 읽기 QD를 높이는 조건을 검토한다.

## 4. 일정 (4주, 보수적)

| 주 | 단계 | 보수적 시간 | 통과 기준 |
|---|---|---|---|
| 1 | ① 호스트 단위 시험(재정렬 함수 분리) → ② 보드에서 "앞지를 수 있던 횟수"만 기록 | 3~5일 | 호스트 시험 통과, 대기 읽기가 실제로 있음 |
| 2 | ③ 재정렬 켜기(장벽 포함) → ④ `fio verify` 정합성 | 4~6일 | 검증 오류 0, 멈춤 없음 |
| 3 | ⑤ 관문 측정(플래그 off, QD1 3회) → ⑥ 제안 QD1 3회 | 3~4일 | off가 앞 값과 일치 |
| 4 | ⑦ 해석, 보고서(필요하면 QD8 3 + 보충 2) | 3~5일 | 결과를 논문 문장에 쓸 수 있음 |

- 측정은 짧고 병목은 ③④의 디버깅이다. 구현과 검증 시간은 과거 기록이 없어 **추정**이다.
- 하루 보드 회차는 4~5회가 한계이고 재실행 25~40%를 여유로 잡았다.
- 한 단계의 관문을 못 넘으면 다음으로 가지 않고 그 단계를 연장한다.

## 5. 성공 기준 (측정 전에 팀이 정할 것)

- **필수:** 정합성 오류 0, 앞 실험과 같은 조건(관문 통과), 쓰기 IOPS 손실을 수치로 보고
- **목표:** QD1에서 `W_die`가 R-Buf FIFO보다 의미 있게 줄고 p99도 따라 줄 것. 임계값(예: `W_die` 평균 절반 이하)은 제안이며 팀이 정한다.
- 모형상 `W_die`는 약 8.4ms에서 최대 0.58ms 수준이지만 이상적 상한이다. 약속하지 않는다.

## 6. 결과에 따른 논문 문장

| 상황 | 쓸 내용 |
|---|---|
| 효과 있음 | `W_die`와 p99 감소, 쓰기 비용 |
| `W_die`는 줄었는데 p99 불변 | 다른 단계가 남음을 단계별 분해로 보임 |
| 효과 작음, 앞지른 횟수 적음 | 대기 읽기가 드물어 효과가 제한된다는 분석(카운터가 근거) |
| 구현 지연으로 측정 못 함 | 설계, 호스트 단위 시험, 기록-only 결과 + 한계 명시 |

## 7. 위험과 대응

- 읽기 중간 끊김이나 멈춤 → 재정렬 조건을 "헤드가 처음 시작하는 요청"으로 더 좁힌다.
- 관문(off 빌드)이 앞 값과 다름 → 호스트 설정(`/proc/cmdline`의 폴링)과 빌드 차이부터 찾는다.
- 같은 블록 읽기·쓰기 정합성 → `fio verify`를 주소가 겹치는 조건에서 별도로 돌린다. 이 시간은 기록이 없다.
- 기록 용량 초과 → ROT 또는 쓰기 구간 축소.

## 8. 확인하지 못한 것

- 구현·정합성 검증에 걸리는 실제 시간
- 한 회차의 실제 소요(덤프 시간 미측정)
- `permittedProgPage`가 정확히 언제 올라가는지(재정렬과의 의존성 겹침)
- 64B 레코드에 앞지른 횟수를 넣을 여유 필드가 있는지
- 위 회차 수 중 "유입률 낮춘 조건"은 보고서에 수준 수가 없어 가정한 값
