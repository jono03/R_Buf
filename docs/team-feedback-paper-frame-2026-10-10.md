## 2. 표현 수위 점검

### 2.1 "SSD 내부가 아니라 완료 인터럽트 경로" (✗)

- **틀의 문장:** 주장 문단 "즉 이 정지는 SSD 내부 처리가 아니라 완료 인터럽트 경로의 현상이다", 기여 2 "호스트 지연만 보면 … SSD의 read stall로 오인".
- **확인된 것:** 정지한 읽기의 펌웨어 시간은 0.35~1.24 ms(R1 5건 직접 대조, 정지 시간의 99.99%가 펌웨어 구간 밖). 폴링으로 받으면 0건(3회), 같은 큐 구성의 인터럽트로 받으면 9건(2회, 엔진 두 가지).
- **확인 못 한 것:** 인터럽트가 빠지는 **원인**. 팀 문서도 이를 미확인으로 적었습니다. 그런데 완료 인터럽트(MSI-X)를 만들어 내는 쪽은 보드의 NVMe 컨트롤러 하드웨어(= SSD 쪽)일 수도 있습니다. 폴링은 인터럽트 없이 완료 큐를 직접 읽으므로, "인터럽트 경로의 어딘가"까지만 가르고 호스트인지 장치인지는 가르지 못합니다.
- **고칠 문장 (제안):**
  "호스트가 본 초 단위 읽기 정지는 펌웨어가 읽기 요청을 처리하는 구간(버퍼·die 큐·NAND·DMA) 밖에서 생기며, 읽기 완료를 인터럽트 대신 폴링으로 받으면 사라졌다. 인터럽트가 지연되는 원인(장치 측인지 호스트 측인지)은 확인하지 못했다."
- 기여 2의 "SSD의 read stall로 오인"도 "펌웨어 구간 분해 없이는 정지 위치를 알 수 없다" 정도로 낮추는 것을 권합니다.
- 부수 확인: 원인 미확인이라는 한계 문장은 이미 있습니다. 주장 문단과 모순되지 않게 하는 것이 요점입니다.

### 2.2 "펌웨어 내부 꼬리 지연을 줄인다(최대 약 21~29 → 10 ms)" (✗)

- 실측: **QD1** 펌웨어 최대 S-Buf 20~25 ms, R-Buf 약 10 ms. **QD8** 펌웨어 최대 S-Buf 28.8 ms, R-Buf **38.8 ms**(R-Buf가 더 큼).
- 문장 앞부분의 "21~29"는 QD1 S-Buf(20~25)와 맞지 않습니다. 29는 QD8 S-Buf(28.8)에서 온 숫자로 보입니다. 출처를 확인해 QD1 값만 쓰세요.
- 고칠 문장: "읽기 QD1에서 R-Buf는 … 펌웨어 내부 최대 지연을 S-Buf의 20~25 ms에서 약 10 ms로 줄인다. 읽기 QD8에서는 칸 재사용 막힘 때문에 버퍼 대기가 다시 생겨 줄지 않았다(최대 28.8 → 38.8 ms)."
- 위 마지막 문장은 보조 결과로 이미 있습니다. 핵심 문장에는 QD1 한정만 명시하면 됩니다.

### 2.3 "R-Buf로도 정지 시간이 거의 그대로" (△)

- 정지 합(끝 1건 제외): S-Buf 8.9 / 30.6 / 52.0 s, R-Buf 53.6 / 48.0 / 54.5 s. S-Buf 안에서도 변동이 매우 큽니다. 반복이 3회라 순위·증감을 말할 수 없습니다(틀의 "쓰지 않는 것"과 같은 이유).
- 고칠 문장: "R-Buf에서도 초 단위 정지가 남는다(3회 모두 10~16건)."
- 비교 문장("그대로")은 빼세요.

## 3. 틀 내부 불일치

### 3.1 그림 1의 "(주 결과)" 표기 (✗)

- 틀은 두 가지를 동시에 말합니다. ① 그림 1 = 폭주 구간 p99 초과 읽기의 구간 구성(2층)이며 "(주 결과)". ② 사전 판정 규칙 적용 결과 **주 결과 = 1층(호스트 정지, 펌웨어 밖)**, 결과 절 배치도 호스트 정지가 먼저.
- 현재 그림 번호는 부 결과(2층)가 그림 1, 주 결과(1층, 시계열)가 그림 2입니다. 결과 절 서술 순서(표 1 → 표 2 → 그림 1 → 그림 2)도 부 결과가 먼저입니다.
- 제안: 그림 2(호스트 정지 시계열)를 그림 1로, 구간 구성을 그림 2로 바꾸고 "(주 결과)"는 호스트 정지 쪽에 붙입니다. 결과 절 순서는 표 1 → 호스트 정지(그림 1) → 펌웨어 안 꼬리(그림 2, 표 2) → M2로 정리합니다.

### 3.2 기여 번호 (△)

- 1, 2, 4, 3 순서로 적혀 있습니다. 보조 기여(R-Buf 최소 재현, 번호 3)와 칸 재사용 막힘(번호 4)의 위치를 바꾸거나 번호를 다시 매기세요.

### 3.3 그림 2의 "정지한 읽기의 펌웨어 시간 표시" (△)

- 이를 그리려면 호스트 정지 읽기를 펌웨어 레코드와 짝짓는 과정이 필요합니다. 지금까지 확인한 것은 R1 5건의 직접 대조와, 나머지 회차의 **최대값 비교**(짝짓기 없음)입니다.
- 그림에 점으로 찍으려면 짝짓기 근거(LBA와 시각, `trace_lookup.py`)를 4절에 한 줄 쓰고, 짝짓기 못 한 정지는 몇 건인지 표기하세요. 짝짓기 불가는 "펌웨어 최대 10 ms < 호스트 정지 1 s"라는 최대값 비교로 대체한다고 밝히면 됩니다.

## 5. 한계 절에 추가할 것 (틀에 없거나 약한 것)

1. **정지 분모 정의:** `rbuf2` 비교를 쓰지 않는 이유 (위 4절).
2. **새 분석 도구 미검증:** `trace_phases`·`trace_loopdie`·`trace_where`는 합성 데이터로만 테스트. 표 2·그림 2의 수치는 실제 덤프에 돌린 뒤 확정.
3. **빌드 동일성:** E1과 SDK 프로젝트의 ELF 해시 부재, `[GC]` 출력 유무 차이(전 회차 `gcCnt` = 0).
4. **폴링은 읽기에만 적용:** 쓰기는 인터럽트 그대로. "완료 경로"는 읽기 완료 경로를 뜻함.
5. **쓰기 쪽 계측 부담 미측정.**
6. **끝 1건(종료 시점 30초급):** 커널 I/O timeout(30 s)과 연관, S2·S3·R1에서만. 표에서 별도 열로 분리.
