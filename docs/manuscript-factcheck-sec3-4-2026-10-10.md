# 원고 3절(구현과 검증)·4절(측정 방법) 사실 확인용 근거표 — 2026-10-10

초안 본문 없이 작성한 것이다. 원고에 들어갈 가능성이 높은 주장마다 근거와 쓸 수 있는 문구 수준을 정리했다.
초안이 오면 이 표와 문장 단위로 대조한다. ✔ = 이 저장소·실측으로 확인, △ = 단서를 붙여야 함, ✗ = 확인 못 함(쓰지 말 것).

## 1. 3절: 구현과 검증

| 주장 | 판정 | 근거 / 쓸 수 있는 수준 |
|---|---|---|
| 계측 커밋이 R-Buf 로직을 바꾸지 않았다 | △ | `TRACE_ENABLE=0`으로 전처리하면 계측 전(`64af2de`)과의 차이가 빈 문장 `do {} while(0);`, 훅용 중괄호·`else`, assert `__LINE__` 3줄 이동뿐. `data_buffer.c` 로직·`request_transform.c` 로직 불변. **계측을 켠 실측 빌드는 같은 로직에 기록 호출이 추가된 것**(FTL 상태는 쓰지 않으나 타이밍은 바뀜) |
| 정합성 검증이 계측 전 빌드에서 통과했다 | △ | 핵심 1종(좁은 영역 읽기·쓰기 혼합 verify)은 계측 전 빌드. **계측 빌드에 대한 재검증은 하지 않았다** — 위 소스 비교가 간접 근거 |
| E1이 계측 전 빌드로 측정됐다 | △ | 10/7 측정. 업로드된 SDK 프로젝트(10/8)와 **같은 빌드라는 증거(ELF 해시)가 없다**. "계측 전 빌드로 측정"까지만 쓰고 소스 동일은 단정하지 않는다 |
| 읽기 칸 8, 쓰기 칸 120 | ✔ | `RBUF_ENTRY_COUNT = 1 × USER_DIES`(USER_DIES 8), 전체 버퍼 `16 × USER_DIES` = 128칸 |
| 기본 빌드는 S-Buf, R-Buf는 컴파일 옵션 | ✔ | `RBUF_ENABLE` 기본 0, `-DRBUF_ENABLE=1`로 켬. 업로드 SDK 프로젝트는 기본값이 1이므로 **빌드별 ELF 이름으로 구분**(`sbuf_trace.elf`, `rbuf_trace.elf`) |
| GC가 측정에 영향을 주지 않았다 | ✔ | 전 회차 UART `[GC]`와 헤더 `gcCnt` 모두 0. 단 E1 시점 빌드에는 `[GC]` 출력 자체가 없었음(각주 한 줄) |
| 칸 재사용 막힘은 최소 재구현의 성질 | ✔ | `AllocateDataBuf`가 읽기 리스트 LRU 꼬리를 `blockingReqTail` 확인 없이 가져감. `rbuf16` 진단(칸 16)에서 `check_wrap` 99.2%(칸 8은 99.7%)로 N 의존 확인. **원 논문의 성질이라고 쓰지 말 것** |
| R-Buf 성질 기준 | ✔ | "읽기가 쓰기 내려쓰기를 기다리지 않는다"(`bufReadEvictCnt` = 0) |
| 원 논문과 같은 방향(E1) | △ | 방향만. 폭은 작음(v23 한계 참조) |

## 2. 4절: 측정 방법

| 주장 | 판정 | 근거 / 쓸 수 있는 수준 |
|---|---|---|
| 요청별 64 B 레코드, 최대 500,000개 | ✔ | `TRACE_MAX_RECORDS` 500000, 헤더 4 KB + 레코드. 최대 실측 덤프 17,630,592 B = 4096 + 275,414 × 64 (`q4uring1`) |
| 트레이스는 DRAM `0x00300000` 이후 | ✔ | RESERVED0(`0x00300000`~`0x0FFFFFFF`) 안, 최대 끝 주소 약 `0x02185800`. 펌웨어 사용 영역과 겹치지 않음 |
| 타이머 500 MHz, 단위 0.128 µs | ✔ | 시간 단위는 shift 6(64 tick) |
| 덤프는 JTAG/XSCT `mrd` | ✔ | 실행 중 쓰지 않고 fio 종료 후 덤프 |
| 구간 정의 | ✔ | 버퍼 = `dEnqueue − dBufAlloc`, die 큐, 루프, xferwait, nanddma. 폴링 보정·호출 횟수 규칙 보조 보기는 전 회차에서 주 보기와 동일 |
| 호스트 지연 + 펌웨어 로그 결합 | ✔ | fio `write_lat_log`(`ro`/`reader`)와 펌웨어 레코드를 시각으로 대응. `fetch-before` = 호스트 − 펌웨어에는 DMA 이후가 포함 |
| 계측 부담 | △ | 읽기만 IOPS가 `rbuf2`(4,364) 대비 R1 −0.9%, R2 −1.4%, R3 −0.9% (MiB/s 0.1 단위 반올림 ±0.3%p). **쓰기 쪽 부담은 측정하지 않음** |
| 정지는 펌웨어 서비스 구간 밖 | ✔ | 펌웨어 안 1초 이상 정지 0건, 호스트 정지는 폴링 완료로 0건(폴링 3회 0건, 인터럽트 대조 각 9건) |
| 폴링이 정지를 없앴다(엔진 아님) | ✔ | 같은 큐 4+4·같은 `io_uring`에서 `hipri` 유무만 다름. fio 두 파일은 `hipri=1` 한 줄만 다름(diff 확인). 쓰기(`writer`)는 전부 libaio·인터럽트 |
| 폴링 회차를 본 실험 표에 섞지 않음 | ✔ | 호스트 설정이 다름(커널 인자 `nvme.poll_queues=4`, 큐 구성) → 대조 쌍으로만 |
| 전체 읽기 p99로 S/R 크기 비교 | ✗ | 폭주 중 읽기 수가 구성마다 달라 혼동됨. **폭주 구간(storm-only) 값만** |
| rbuf2와 정지 시간 비율 비교 | ✗ | `rbuf2`는 "실행 시간" 기준(73%/75%), 우리 M1 합은 "쓰기 폭주 시간" 기준. 분모 통일 전에는 쓰지 않음 |
| 인터럽트가 빠지는 원인 | ✗ | 미확인. 관리 큐(nvme0q0) 인터럽트 약 20만 건과 IRQ 비활성화는 관찰 사실로만 |
| 정지 위치 판정 | △ | QD1 앞뒤 간격 방법 하나. `trace_where.py` 교차 확인은 하지 않음 |
| 새 분석 도구(`trace_phases`, `trace_loopdie`, `trace_where`) | △ | 합성 데이터 테스트만 통과, 실제 덤프에는 아직 미실행. 결과 표에 쓰기 전에 실제 덤프로 확인 필요 |

## 3. 원고 문장 제안 (사실 범위 내)

- 구현: "실습실 펌웨어(GreedyFTL 기반) 위에 §4.2의 R-Buf를 최소 재구현했다(읽기 칸 8, 쓰기 칸 120). 기본 빌드는 S-Buf이며 `RBUF_ENABLE`로 전환한다."
- 정합성: "정합성은 좁은 영역 읽기·쓰기 혼합 verify로 확인했다(계측 전 빌드). 계측 코드는 `TRACE_ENABLE=0`으로 전처리하면 계측 전 소스와 빈 문장 추가·중괄호 정리 외에 차이가 없음을 확인했다(실측은 `TRACE_ENABLE=1` 빌드)."
- 계측 부담: "계측을 켠 R-Buf의 읽기 전용 처리량은 계측 없는 빌드 대비 약 1%(0.9~1.4%) 낮았다."
- 폴링 대조: "같은 큐 구성과 같은 읽기 엔진에서 완료를 폴링으로 받으면 정지가 0건(3회), 인터럽트로 받으면 9건(2회)이었다. 쓰기 경로는 모든 회차에서 인터럽트였다."
